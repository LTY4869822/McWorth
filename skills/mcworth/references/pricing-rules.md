# 金额记账规则

四个数字口径不能混为一谈。混了就是在给用户报错账。

## 四种口径

| 口径 | 定义 | 何时可用 |
|---|---|---|
| **已核价同餐盘差额** | 已核价基准总额 − 已核价候选总额 | **仅当两个餐盘完全一致**（`plate_hash` 相同） |
| **方案差额** | 不同餐盘/履约的两个已核价金额之差 | 餐盘不一致时，**只能**用这个口径 |
| **实际现金支出** | 官方确认支付的订单金额 | 订单创建成功后 |
| **已核价方案累计差额** | 多次配餐的同口径之和 | 用户主动要求累计时 |

## 判定流程

```text
两条路径都有官方报价？
├─ 否 → 不报任何差额，如实说明未核价
└─ 是 → plate_hash 相同？
         ├─ 是 → 「与原购买组合相比低 ¥X（相同餐盘差额）」
         └─ 否 → 「低 ¥X（方案差额，不是无代价节省）」
```

## 三条禁令

1. **没有基准不报节省额。**基准 = 用户原购买计划的已核价结果。用户没说过原计划，就没有比较对象。
2. **未核价的金额不展示。**本地估算（菜单价 + 差价推导）只用于内部排序候选，一旦出现在用户面前就等于伪造报价。
3. **餐盘不一致时不得省略说明。**"低 ¥2.50"单独出现会让人以为是净赚，实际是多吃了一杯饮料换来的。

## 单位

一律整数分。菜单里的字符串价格（`"22.5"`）转换时禁止走浮点中间态。

## 证据

每个展示给用户金额都应能回溯：

- 官方核价时间
- 官方 `traceId`
- 门店 / 履约上下文

缺失任一项，说明这个金额没有经过完整核验链路。
